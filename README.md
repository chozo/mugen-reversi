# 無限オセロ（mugen othello）プロトタイプ

通常のオセロから「盤面の境界」だけを取り除いた、無限盤オセロのWebプロトタイプ。

目的は完成品ではなく、**「角も辺も存在しないオセロは、ゲームとして面白いのか」** を実際にプレイして検証すること。

コンピュータとの対戦専用（強さは4段階）。人同士の対戦はない。

**遊ぶ: https://game.chozo.net/mugen-othello/**

## コンセプト

- 8×8 の盤では「角」と「辺」が強い場所になる。盤面そのものを無限にして、角と辺をなくす。
- 変えるのは原則これだけ。石の数は通常のオセロと同じ（各32個）にして、**「有限の石 × 無限の盤面」** でどんなゲーム性が生まれるかを見る。
- 見た目も「盤の上に石を置く」のではなく、「無限の方眼空間に石を置く」感覚にする。盤の枠は描かない。

## 現在のルール

| 項目 | 内容 |
| --- | --- |
| 盤面 | 境界のない無限グリッド（負の座標を含む任意の整数座標） |
| 初期配置 | (0,0) 白・(1,0) 黒・(0,1) 黒・(1,1) 白（y は下向き） |
| 先手 | 黒 |
| 石の数 | 各32個。初期配置で2個ずつ使うので、ゲーム中に置けるのは各30個（最大60手） |
| 手持ち石 | 「ゲーム中に新しく盤へ置ける石の数」。反転で色が変わっても増減しない |
| 着手 | 縦・横・斜めの8方向で、相手の石を1個以上挟める場所にだけ置ける。挟んだ石はすべて自分の色になる |
| パス | 手持ち石はあるが合法手がない場合、自動でパス。相手が続けて打つ |
| 石切れ | 手持ちを使い切ったプレイヤーは以後打てない。相手に手持ちと合法手があれば、相手だけが続けて打つ |
| 終局 | ① 両者とも打てない（合法手がない、または石切れ）② 双方が石を使い切った |
| 勝敗 | 終局時の盤上の石数が多い方の勝ち。同数は引き分け |

ルールは依頼時の仕様のまま実装している。問題点や改善案は [発見したゲームデザイン上の問題](#発見したゲームデザイン上の問題) に記録し、ルール自体は変えていない。

## タイトル画面

起動するとタイトル画面を表示する。このオセロの特徴と操作方法を説明し、「あそぶ」で対戦設定へ進む。「あそぶ」は紹介文のすぐ下（スクロールせずに押せる位置）と、説明の最後の2か所にある。

- 紹介文: 「無限に広がる盤面で、通常のオセロと同じ32枚の石を置いて戦うオセロです。」
- 特徴: 盤面に端がない／石は32枚ずつ（置けるのは30枚、返されても手持ちは増えない）／ルールはオセロのまま
- 操作方法: 石を置く・盤面を動かす・拡大縮小・全体を見る（スマホと PC の両方）
- ひとこと: 「盤面を広く使って、全体の戦況を確かめながら戦いましょう。」と、画面外の合法手の赤い点の説明
- 盤面のイラスト（SVG）は、グリッドが端に向かって消え、遠くの石ほど薄くなる。無限に続く盤面を表す
- 対局中も「New Game」→ 対戦設定の「遊び方」でタイトル画面を見られる。画面に収まらない場合はスクロールする

## 対戦設定

タイトル画面の「あそぶ」と「New Game」で対戦設定を開く。

| 項目 | 選択肢 |
| --- | --- |
| コンピュータの強さ | かんたん / ふつう / つよい / げきむず |
| あなたの石 | 黒（先手） / 白（後手） |

対局中に「New Game」を押しても、「キャンセル」で対局に戻れる。

### コンピュータの強さ

| 強さ | 考え方 | 1手の思考時間 |
| --- | --- | --- |
| かんたん | 合法手からランダムに選ぶ | すぐ |
| ふつう | 1手先だけを見て、最も得な手を選ぶ（ほぼ「最も多く返す手」） | すぐ |
| つよい | 3手先まで読む | 数十ミリ秒 |
| げきむず | 2秒の間、読める限り深く読む（反復深化）。残り手数が少なければ最後まで読み切る | 約2秒 |

- 共通の仕組み: アルファベータ法による探索。評価は「石差」と「次の手番の側が1手で増やせる石差の半分」。同じ評価の手が複数あればランダムに選ぶので、毎回同じ展開にはならない。
- 「げきむず」は PC（Apple Silicon の Chrome）で序盤〜中盤に6〜9手先まで読み、残り6手ほどから最後まで読み切る。スマホでは読める深さが浅くなる。
- CPU が打つ前に最低0.45秒の間を置き、直前の反転アニメーションが終わってから打つ。
- 思考は Web Worker（別スレッド）で行うので、考えている間も盤面の移動・拡大はできる。

強さの序列は `npm run sim:ai`（各10局、先後を入れ替え）で確かめた。

| 対局 | 結果 | 強い側の平均石差（黒番 / 白番） |
| --- | --- | --- |
| ふつう vs かんたん | 10勝 0敗 | +35.2 / +50.0 |
| つよい vs ふつう | 9勝 1敗 | +12.4 / +28.4 |
| げきむず vs つよい | 5勝 0敗 5分 | 0.0 / +24.0 |

「げきむず」は白番では全勝したが、黒番では5局すべて引き分けだった。終盤を読み切ったうえで「引き分けが最善」と判断して引き分けている（不具合ではない）。白の有利が大きいためと考えられる（[問題 1](#1-最後に打つ側ほぼ常に白が有利になりやすい)）。

## 操作

| 操作 | スマートフォン | PC |
| --- | --- | --- |
| 石を置く | 薄い点のマスをタップ | クリック（合法手の上では半透明の石が出る） |
| 盤面の移動 | ドラッグ / スワイプ | マウスドラッグ・矢印キー |
| 拡大・縮小 | ピンチ | ホイール・トラックパッドのピンチ・`+` / `-` |
| 全体を表示 | 「全体表示」ボタン | `F` |
| 音の ON / OFF | 「音 ON」ボタン | `M` |
| 新しい対局 | 「New Game」→ 対戦設定 →「はじめる」 | 同左 |

盤面を探索しやすくするための表示:

- **ミニマップ**（右下）: 全ての石と、いま見えている範囲（赤枠）。タップするとその場所へ移動する。
- **画面外の合法手**: 画面の外に合法手があると、その方向の画面端に赤い点が出る。
- **全体表示**: 全ての石と合法手が収まるように、拡大率と位置をなめらかに変える。
- 直前の着手には赤い点が付く。

## 音

BGM と効果音は、音源ファイルを使わず Web Audio API でその場で合成している（`src/audio.ts`）。

| 音 | 内容 |
| --- | --- |
| BGM | 明るいポップス（Cメジャー・116 BPM・16小節で約33秒のループ）。A: C → G → Am → F → C → G → F → G、B: F → G → Em → Am → F → G → C。メロディ（矩形波に1オクターブ上の三角波を薄く重ねる）、裏拍の和音、オクターブと5度ではずむベース、ドラム（4つ打ちのキック・2拍と4拍のクラップ・8分のハイハット、4小節ごとのつなぎ）。メロディは `src/audio.ts` の `MELODY` に1小節8音で書いてある |
| 打った音 | 木の駒を置いたような短い「コトッ」。CPU（白のとき）は少し高い |
| 返す音 | 石の色が変わる瞬間に軽い「チッ」。置いた石から遠い石ほど音が高くなる（ペンタトニック）。同じ距離の石は同時に返るので1回にまとめ、数が多いほど少し大きくする |

- ブラウザの自動再生制限のため、対戦設定の「はじめる」を押したときに音を有効にして BGM を始める。それまでは音を出さない。
- 「音 OFF」で BGM と効果音を止める（音声処理も停止する）。設定は保存しない。「音 ON」に戻すと4小節の区切りから再開する。
- 画面が隠れている間（別のタブ・アプリに切り替えたとき）は止まる。
- 音量の目安（`npm run e2e` で書き出して測定）: BGM のみ RMS 約 -43 dBFS・ピーク約 -25 dBFS（`audio.bgm` = 0.08）、効果音を重ねたときのピーク約 -5 dBFS。BGM は効果音より十分小さくしている。音量は `src/config.ts` の `audio` で調整する。
- `npm run e2e` は試聴用に `bgm.wav`（BGM 30秒）と `bgm-with-se.wav`（BGM と効果音 12秒）をスクリーンショットと同じ場所に保存する。

## 技術構成

- **Vite + TypeScript**（素の DOM と Canvas 2D）。フレームワークは使っていない。
  - ゲームの状態はルール本体の `Game` だけが持ち、UI は小さいので、フレームワークを入れる利点がない。
  - 盤面は Canvas に毎フレーム描く。見えている範囲のマスと石だけを描画する。
- **Web Worker**: コンピュータの思考を別スレッドで行う（Vite の `new Worker(new URL(...), { type: 'module' })`）。
- **Vitest**: ルールとコンピュータの単体テスト。
- **playwright-core** + インストール済みの Chrome: ブラウザでの動作確認（`tools/e2e.mjs`）。
- **wrangler**: Cloudflare Workers（静的アセット）への公開。
- **ffmpeg-static**: 告知動画の書き出し（`npm run promo`）。
- 実行時の依存ライブラリはない（devDependencies のみ）。

### 無限盤の実装

- 論理盤面は `Map<"x,y", "B" | "W">`。固定サイズの配列は使わない。
- **合法手の探索**: 合法手は必ず相手の石に隣接する空マスなので、「相手の石の8近傍にある空マス」だけを候補にして、各候補から8方向を調べる。盤上の石の数に比例する計算量で、無限盤全体は走査しない。テストで、石の外接矩形を総当たりした結果と一致することを確認している。
- **反転判定**: 置いた位置から各方向へ相手石が続く限り進み、その先が自分の石なら挟める。石は有限個なので、必ず空マスで止まる。
- **コンピュータの探索**: `Game` は使わず、座標を1つの整数にした `Map<number, 1 | -1>` の盤面で、着手を「打つ・戻す」の差分更新で読む。合法手の探し方は `Game` と同じ（相手の石の8近傍の空マスだけ）。
- **描画**: カメラの中心座標と1マスの大きさ（px）から、画面に入るマスの範囲を求め、その範囲のグリッド線と石だけを描く。縮小したときはグリッド線を薄くする。

## 起動方法

```sh
npm install
npm run dev        # 開発サーバ（--host 付きなので同じネットワークのスマホから開ける）
npm test           # ルールの単体テスト
npm run build      # 型チェック + dist/mugen-othello/ へ出力
npm run e2e        # ブラウザでの動作確認（先に npm run build）
npm run sim        # 自動対局で傾向を測る（npm run sim -- 1000 で局数を指定）
npm run sim:ai     # コンピュータの強さ同士を対局させる（npm run sim:ai -- 20 で局数を指定。げきむずは1手2秒かかる）
npm run deploy     # build してから Cloudflare Workers へ公開
node tools/make-og.mjs  # OGP 画像を作り直す
npm run promo      # 告知動画を作る（下の「告知動画」を参照）
```

`npm run e2e` は macOS の Chrome（`/Applications/Google Chrome.app`）を使う。`E2E_URL=https://game.chozo.net/mugen-othello/ npm run e2e` で公開URLに対しても実行できる。別の場所なら `CHROME_PATH` で指定する。スクリーンショットは `E2E_OUT`（未指定なら OS の一時ディレクトリ）に保存する。

## 告知動画

縦型 1080×1920・約29秒・30fps の告知動画を、実際のゲーム画面を1コマずつ撮影して作る（`tools/promo/`）。

```sh
npm run promo                        # build してから全コマを撮影し、MP4 に書き出す
PROMO_EVERY=15 npm run promo         # 確認用: 15コマおきの一覧画像だけ作る（構成の確認に使う）
PROMO_ENCODE_ONLY=1 npm run promo    # 撮り直さずに、音と書き出しだけやり直す
PROMO_SEED=4 npm run promo           # 乱数の種を変えて、別の展開で撮る
```

- 出力先はアプリのフォルダの隣の `../video/`（リポジトリには含めない）: `mugen-othello-promo.mp4`（本編）、`-cover.jpg`（表紙）、`-sheet.jpg`（2秒おきの一覧）。途中ファイルは `../video/work/`。
- 構成（`tools/promo/scenario.js`）: スローで16枚を一気にひっくり返すつかみ → タイトル → 最初から実際のプレイ（タップで置く・早送りで盤面が広がる・スワイプで移動）→ 終盤「最後の1手まで逆転あり！」→「勝った〜！」→ エンドカード（公開URL）。
- 「あなた」（白）の手は、台本の中で「多く返せて盤面の中心に近い手」を選んでタップする（強いコンピュータ同士だと直線を伸ばし合う細長い盤面になり、画面映えしないため）。最後の数手だけコンピュータ（つよい）の読みを使う。相手はコンピュータ（ふつう）。種 5 で、あなたが白34-黒30で勝つ展開になる。
- 音: ゲームの BGM と効果音を、普段と同じ合成関数で書き出し、-14 LUFS・真のピーク約 -2 dBTP に合わせる。外部の音源は使っていない。
- ゲーム側には撮影用の入口を `window.__game` に足している（`manual` / `step` / `drainEvents` / `audio` / `promoBgm` / `bestMove` / `touchDown` など）。撮影中だけゲーム内の時計で進み、普段の遊び方・見た目は変わらない。

## 発見したゲームデザイン上の問題

以下は、ルールの分析と `npm run sim` の自動対局から見つけたもの。自動対局は単純な戦略（ランダム、最も多く返せる手、相手の合法手を最も減らす手）なので、人間のプレイでも同じことが起きるかはまだ確かめていない。ルールは変えていない。

### 自動対局の結果（`npm run sim`）

| 対局 | 局数 | 黒勝ち | 白勝ち | 引分 | 平均手数 | パスが起きた局 | 平均の広がり | 最大の辺 | 平均石差 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| ランダム vs ランダム | 500 | 32.0% | 62.4% | 5.6% | 60.0 | 0% | 11.6×11.6 | 16 | 8.8 |
| 最大反転 vs 最大反転 | 500 | 21.2% | 75.8% | 3.0% | 60.0 | 0% | 28.2×27.8 | 45 | 22.6 |
| 機動力 vs 機動力 | 200 | 49.5% | 46.5% | 4.0% | 59.8 | 0% | 12.6×12.5 | 28 | 20.4 |
| 機動力(黒) vs 最大反転(白) | 200 | 0.5% | 99.0% | 0.5% | 56.0 | 1% | 13.7×13.9 | 27 | 46.5 |
| 最大反転(黒) vs 機動力(白) | 200 | 96.0% | 4.0% | 0% | 55.1 | 6% | 14.3×14.2 | 35 | 37.8 |

### 1. 最後に打つ側（ほぼ常に白）が有利になりやすい

- 無限盤ではパスがほとんど起きない（上の表でほぼ0%）。そのため、ほぼ必ず黒30手・白30手を交互に打ち、**60手目（最終手）は白**になる。
- 角と辺がないため、**確定石がほとんど存在しない**。ある直線上で石の両端が空マスなら、後から挟まれる可能性が残る（両端が相手の石で挟まれた形だけが、その直線について安定する）。
- その結果、最後の1手でまとめて返した側が勝ちやすい。ランダム同士で白62%、最大反転同士で白76%。
- **強いプレイ同士ほど白の有利が大きくなる。** 読みの深さを固定して対局させると、深さ5で読む黒は深さ3で読む白に8局中1勝もできなかった（白番では8局全勝）。コンピュータの「げきむず」も、黒番では「つよい」に勝てず引き分けにとどまった。
- 改善案（未実装）: 先後を交互にして2局1セットにする、白の手持ちを1個減らすなどのハンデを付ける、など。

### 2. 「相手の打てる場所を減らす」戦略が通用しない

- 通常のオセロでは、相手の合法手を減らす（機動力を奪う）戦略が強い。この盤では、それが「最も多く返す」戦略に大敗した（96〜99%）。
- 盤が無限なので、相手を打てなくする（パスさせる）ことがほぼできない。合法手を減らしても、相手にはどこかに打つ場所が残る。
- 単純に多く返す手が強いだけのゲームになっていないかは、人が実際にプレイして確かめる必要がある。

### 3. パスと「石切れ」のルールがほぼ働かない

- パスがほぼ起きないので、「片方だけ石を使い切り、相手が続けて打つ」場面もほとんど起きない。終局は、ほぼ必ず「60手を打ち切った時点」になる。
- 例外は全滅（片方の石が盤上から消える）。強さに差がある対局では22〜24%で全滅が起きた。全滅すると両者とも打てなくなり、その時点で終局する。

### 4. 返す手を優先すると盤面が大きく広がる

- 最大反転同士では、石の範囲が平均で約28×28、最大で45マスの辺になった（石は最大64個なので、ほとんどが空き）。長い直線を伸ばして挟み合う形になりやすい。
- 28マス以上の範囲をスマホの画面に収めると、1マスが10px程度になり、石の色の判別が難しくなる。ミニマップと全体表示で補っているが、人間のプレイで状況が把握できるかは要確認。
- ランダム同士では約12×12で、通常の8×8より少し広い程度。

### 5. 強いコンピュータ同士では、直線を伸ばし合う細長い盤面になる

- 告知動画の撮影で「つよい」同士を対局させると、両者が石を一直線に伸ばし合い、盤面が縦横の細長い線になった（[今後検証したい項目](#今後検証したい項目) の2「戦線が一方向へ伸び続けるだけのゲームにならないか」にあたる）。
- 長い直線は一度に多くの石を返せるので、数手先を読む評価（石差）では有利に見えるためと考えられる。人のプレイでも起きるか、起きたときに面白いかは要確認。

### 6. 終盤に「盤を埋める」局面がない

- 通常のオセロの終盤は、残った空きマスの順番の読み合いになる。無限盤では空きマスが尽きないため、この種類の読みがない。
- 終盤の戦略性は「残り手数（手持ち）を見ながら、最後の数手でどれだけ返すか」に集まる可能性がある。

## 今後検証したい項目

実際のプレイで、次を確かめる。

1. 角と辺がなくてもオセロとして成立するか
2. 戦線が一方向へ伸び続けるだけのゲームにならないか
3. 盤面を広げる戦略に意味があるか（離れた場所に打つ・まとめて打つの違い）
4. 盤面が広がりすぎて状況把握が困難にならないか（ミニマップ・全体表示で足りるか）
5. 32個ずつという石数が適切か（少なくした・多くしたときの比較）
6. 終盤に戦略性が残るか
7. 「無限盤だからこそ面白い」と感じられる局面が生まれるか

加えて、プロトタイプで見えた点:

- 白（最終手番）の有利は、人のプレイでも起きるか。人がコンピュータに黒番で勝てるか。
- 「最も多く返す」より強い戦略が人間には見つかるか。
- 確定石に近い形（両端を相手の石で挟まれた列）は、作る価値があるか。
- 手持ち石の数を変えたときの先後の勝率（`new Game({ stock })` で変えられる。自動対局で比較できる）。
